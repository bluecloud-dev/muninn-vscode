What this repo does: Muninn is a desktop VS Code editor for ordinary Markdown, with a ProseMirror editing surface and static HTML export. The VS Code text document owns persistence, and edits must preserve unrelated source bytes ([architecture](ARCHITECTURE.md), [source fidelity contract](ROUNDTRIP_CONTRACT.md)). Expected load is one person with several open documents, local or remote filesystem providers, and normal delays while reading or copying images; this is not a public server.

Validated against runtime source at `045bcfdac33818c1819c9db80808891de3deabca` (v1.4.1). **Both findings are fixed in 1.4.2.** The report below preserves the original evidence; its source and test links point to the audited snapshot. The fixes retain strict image validation and correlate imports with their original document and selection. Current regressions cover large SVGs, delayed reads, changed selections and documents, reordered replies, cancellation, cleanup, and undo/redo in [provider tests](../tests/unit/provider-behavior.test.ts), [bundled-editor tests](../tests/unit/editor-behavior.test.ts), and the [packaged UI journey](../tests/electron/editor.test.mjs).

**Confirmed findings at the audited snapshot (resolved in 1.4.2)**

1. **Supported-size image pastes and drops fail without an explanation** ([src/custom-editor/muninn-custom-editor-provider.ts:738–746](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/custom-editor/muninn-custom-editor-provider.ts#L738-L746))

   - **What this is:** Paste/drop reads an image as base64 in [src/webview/editor/index.ts:269–299](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/webview/editor/index.ts#L269-L299), then the host checks its encoding before copying it. Images up to 10 MiB are supported, including SVG ([README](../README.md#settings), [src/custom-editor/image-assets.ts:7–19,50–66](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/custom-editor/image-assets.ts#L7-L66)).
   - **Problem:** On Node 24.21.0, valid 5 MiB and 10 MiB SVGs cause the repeated-group base64 regex to throw `RangeError: Maximum call stack size exceeded`; the provider writes no file and sends neither success nor rejection. Its outer message handler only logs the exception ([src/custom-editor/muninn-custom-editor-provider.ts:188–199](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/custom-editor/muninn-custom-editor-provider.ts#L188-L199)), leaving the user without an actionable error.
   - **Fix:** Replace the repeated groups with `s.length % 4 === 0 && /^[A-Za-z0-9+/]*={0,2}$/.test(s)`, retaining the encoded-length limit, decoded-size limit, empty-file rejection and type allowlist. Add a provider regression using a valid large SVG; keep strict encoding validation because [Node's base64 decoder also accepts whitespace and the URL-safe alphabet](https://nodejs.org/docs/latest-v24.x/api/buffer.html#buffers-and-character-encodings).
   - **If we skip it:** A normal supported image import can silently fail even though the file is within the advertised limit. The file-picker command bypasses this base64 check, so the confirmed failure concerns paste/drop, not every image-import route ([src/custom-editor/muninn-custom-editor-provider.ts:232–269](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/custom-editor/muninn-custom-editor-provider.ts#L232-L269)).

   **Reproduction:** Generate a legal SVG containing a description and a visible rectangle, encode it, and call the current validator:

   ```js
   const prefix = '<svg xmlns="http://www.w3.org/2000/svg" width="1" height="1"><desc>';
   const suffix = '</desc><rect width="1" height="1" fill="red"/></svg>';
   const bytes = Buffer.from(
     prefix + 'x'.repeat(5 * 1024 * 1024 - prefix.length - suffix.length) + suffix,
   );
   const s = bytes.toString('base64');
   /^(?:[A-Za-z0-9+/]{4})*(?:[A-Za-z0-9+/]{2}==|[A-Za-z0-9+/]{3}=)?$/.test(s);
   // Node 24.21.0: RangeError: Maximum call stack size exceeded
   ```

   The fixture uses the standard [SVG namespace and description element](https://www.w3.org/TR/SVG2/struct.html#DescriptionAndTitleElements). Independent validation parsed each fixture as SVG/XML, bundled the actual provider source in memory, and delivered `view.requestImageInsert` through its registered message listener with filesystem calls mocked:

   | Valid SVG bytes | Files written | Host outcome                    |
   | --------------: | ------------: | ------------------------------- |
   |           1,024 |             1 | `host.imageInserted`            |
   |       5,242,880 |             0 | Logged stack overflow; no reply |
   |      10,485,760 |             0 | Logged stack overflow; no reply |

   The proposed flat check matched the original on 111,111 short inputs, including malformed padding, invalid characters and line breaks; it also accepted 513 generated valid lengths and the 10 MiB fixture. Existing [provider tests:727–740,799–825](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/tests/unit/provider-behavior.test.ts#L727-L825) check malformed/oversized input and a tiny accepted payload, leaving this supported-size case uncovered.

2. **A delayed image reply replaces text selected after the import started** ([src/webview/editor/index.ts:585–604](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/webview/editor/index.ts#L585-L604), [src/webview/editor/image-insertion.ts:47–54](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/webview/editor/image-insertion.ts#L47-L54))

   - **What this is:** Image insertion waits for browser file reading and host filesystem operations before the reply reaches the editor. The reply handler passes the editor's current state to `createImageInsertionTransaction`, whose text-selection branch uses `replaceSelectionWith`; [ProseMirror documents that this replaces the selection](https://prosemirror.net/docs/ref/#state.Transaction.replaceSelectionWith).
   - **Problem:** Start pasting before `Alpha` in `Alpha Beta`, select `Beta` before the host replies, and the resulting Markdown is `Alpha ![Beta](images/…svg)` instead of an image before `Alpha Beta`. The later selection becomes image alt text, and the editor acknowledges success; the import is not tied to the original selection or document ([src/webview/editor/index.ts:1145–1153](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/webview/editor/index.ts#L1145-L1153)).
   - **Fix:** Capture the document and selection before the first asynchronous step, correlate each import with its own token through the request/reply protocol, and restore that selection only if its document is still current, using the existing [link stale-document guard](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/webview/editor/index.ts#L547-L563) and image insertion helper. Cover paste/drop and toolbar/native-command entry points; reject changed-document, unknown or duplicate replies, notify the user, and return `ok: false` for copied-image cleanup through [src/custom-editor/muninn-custom-editor-provider.ts:316–321,837–849](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/custom-editor/muninn-custom-editor-provider.ts#L316-L321).
   - **If we skip it:** Moving the caret or selecting unrelated prose while an image is being read or copied can change the wrong content. Ordinary remote filesystem latency increases the opportunity, although the reproduction needs only a controlled delay and no hostile input.

   **Reproduction:** A fresh in-memory bundle of `src/webview/editor/index.ts` ran in JSDOM with a valid SVG `File` and a controlled `FileReader`; the actual provider, with a mocked filesystem, generated the reply. Pasting at text offset 0, selecting offsets 6–10, and then delivering that reply produced:

   ```text
   Initial Markdown:  Alpha Beta\n
   Requested target:  caret before Alpha
   Later selection:   Beta
   Observed Markdown: Alpha ![Beta](images/image-…svg)\n
   Image result:      ok: true
   ```

   The same result occurred when the selection moved before `FileReader` completed, so capturing it only when sending the host request is too late. Delivering `host.documentChanged` with `New text` before the image reply also inserted the image into that newer content instead of rejecting the stale operation.

   **Concurrency and compatibility:** Two imports completed file reading in reverse order, then received host replies in reverse order; the host correctly created distinct files, but both images landed at the later selection. The existing host `requestId` is allocated only after the write, while the initial [request payload has no correlation token](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/custom-editor/protocol.ts#L133-L141); a single shared pending selection cannot safely identify concurrent imports ([src/custom-editor/muninn-custom-editor-provider.ts:790–810](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/custom-editor/muninn-custom-editor-provider.ts#L790-L810)).

   A scratch prototype using per-request selections and the document-identity guard preserved the original caret and selected table, ignored duplicate replies, and rejected stale or competing results after a document change. Keep the existing helper's text-alt and selected-block behavior; the smallest safe follow-up can reject changed-document imports with a clear retry message rather than introducing position mapping, while [ProseMirror's upload example](https://github.com/ProseMirror/website/blob/master/example/upload/index.js) shows the larger mapped-placeholder approach if imports must survive intervening edits. Native commands also enter through [src/extension.ts:189–192](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/extension.ts#L189-L192) and the [host file picker](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/src/custom-editor/muninn-custom-editor-provider.ts#L232-L269), so a paste-only snapshot would leave that route unprotected.

   Existing tests cover immediate helper insertion, selected text and selected blocks ([tests/unit/image-insertion.test.ts](../tests/unit/image-insertion.test.ts)), a focused table ([tests/unit/editor-behavior.test.ts:1797–1814](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/tests/unit/editor-behavior.test.ts#L1797-L1814)), concurrent file naming and rejection cleanup ([tests/unit/provider-behavior.test.ts:828–938](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/tests/unit/provider-behavior.test.ts#L828-L938)), and the normal native picker journey ([tests/electron/editor.test.mjs:1569–1605](https://github.com/bluecloud-dev/muninn-vscode/blob/045bcfdac33818c1819c9db80808891de3deabca/tests/electron/editor.test.mjs#L1569-L1605)). They do not exercise the delayed selection change above.

**Dependency remediation included in 1.4.2:** The baseline audit JSON contains 22 moderate affected-package entries tracing to two advisories: [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249) (`minimatch <11.0.1`, pattern amplification) and [GHSA-3g3m-2fjr-6pw4](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4) (`glob >=9.0.0 <=14.0.1`, traversal continuing after cancellation). These are two advisories propagated through dependency chains, not 22 distinct security bugs. The [version-scoped overrides](../package.json#L614-L616) now resolve [glob 14.0.3](../package-lock.json#L6524-L6526) and [minimatch 11.0.3](../package-lock.json#L8199-L8201); both are development-only entries, and an independent comparison against the base lockfile found all 148 production entries identical. Every baseline affected node was also development-only. The captured baseline, patched and production-only audit JSON confirms 22 → 0 overall and zero production findings. These [npm overrides](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#overrides) cross major versions; retain compatibility gates and remove them once parent dependencies resolve patched versions themselves ([development guidance](DEVELOPMENT.md)). This establishes dependency hygiene, not a demonstrated exploit against a running editor.

**Original audit verification and limits:** The independent bounded checks ran on Node 24.21.0 and used current source bundled in memory. Provider filesystem calls were mocked, and editor events ran in JSDOM, so these establish the code paths and resulting Markdown rather than native OS clipboard or live remote-provider acceptance.

Local verification recorded a clean Node 24.21.0 install, typecheck, lint, formatting, 393 passing unit/bundled-DOM tests with coverage thresholds met, 58 byte-identical round trips, telemetry scan, packaging/notice freshness and zero audit findings. Native test logs recorded seven extension-host tests on VS Code 1.85.2 and 23 packaged UI tests on stable 1.144.0, on macOS; these logs were reviewed, not rerun here. The native archive preceded a later changelog-only edit with identical product/dependency state, and its normal image journey does not validate either delayed case above. This report records pre-PR local evidence; subsequent hosted checks are attached to the PR.

**Verdict:** Both confirmed image-import findings have focused fixes and regressions in 1.4.2; the dependency remediation is retained.

**Not checked by the original audit:** Full suites were not independently rerun, and this validation did not re-audit every repository module. Manual OS clipboard/dialogs, live SSH filesystem providers, screen readers, abrupt-shutdown recovery, native acceptance of these two reproductions, and independent Windows/Linux reproduction of these two bugs remain unverified.
